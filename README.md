# AI 画板看过来：Easyeda-api-skill 为什么表现不好？

> 原文发布于嘉立创论坛（jlc-bbs.com），作者：坚持不用舵，2026-10-18。
> 原文链接：<https://www.jlc-bbs.com/platform/a/1744383>

最近立创高调推出的那个 AI 画板 skill 也是用了，即 `easyeda-api-skill`，我试图让 AI Agent 实现全链条端到端"设计 + 绘图"，这样我可以彻底解放了（彻底被 AI 取代了 -bushi）。可是它画出来的大概率是错的，错法多种多样，无论用多高级的模型都回天无力。

经过排查，根因是：**"电路连接设计"与"调用工具绘图"未分离成两个独立 Agent，未分离成两个独立上下文。**

## 核心摘要

语言模型在训练阶段就没有学过一种极其轻量的、表达其电路设计思想的中间层描述语言（IR）。因此，在实际使用 `easyeda-api-skill` 过程中经常观察到 Agent 不得不使用自然语言描述一个复杂的电路（往往是生成一个 markdown 文件），这是极其低效的。

人类工程师完成原理图设计时"想"与"画"同构（草稿即工作台），手眼协同，一边画一边想电路，这不会出现什么问题。但是我们现在让大模型帮我们画图，它只会吐字，甚至连思考都靠字之间的上下关系。它在绘图操作时完全依赖大量 tool call 的工具调用请求和查询返回，很大一部分注意力都花在了尽量不写错 JSON 或 JS 标签上。在同一对话中，又操作 EDA、又修改电路拓扑，会使模型注意力涣散。

既然是两种完全不同的注意力结构，就应该放在两个完全不同的对话里，甚至用两种完全不同的模型：

- 专门负责**设计电路**的 **设计 AI Agent**，应当用宏观总领能力更强的基模驱动，如 GPT、Kimi K 系列等等。
- 专门负责**落实到 EDA** 的 **绘图 AI Agent**，则需要工具调用代码生成和输出结构服从性更强的模型驱动，如 GLM、DeepSeek Flash 系列。

理想中的架构是：设计 Agent 产出一份 IR 文件 + 一份 handover.md，交给绘图 Agent，绘图 Agent 再调用 `easyeda-api-skill` 落地到嘉立创 EDA。

## 设计 Agent 怎么把设计思想交给绘图 Agent？

首先想到的是自然语言，这是目前最能想到的解决方案，能从宏观上说明电路的大体拓扑，因此一个 `handover.md` 文件是必不可少的。

但是它无法以高颗粒度描述电路的连接结构。同时为了对语言模型最友好，这个文件必须是纯 unicode 字符写成的。

那这个是什么？有人可能马上想到了：是网表！

立创 EDA 中支持的网表如下：

| 格式 | 面向谁 |
|---|---|
| Protel2 | Altium Designer |
| EasyEDA | EasyEDA 标准版 |
| JLCEDA | 嘉立创 EDA 专业版 |
| PADS | PADS |
| Allegro | Cadence Allegro |
| DISA | 数字化工业软件联盟 |
| DSNET | 数字化工业软件联盟仿真 |

但如果你随便打开一个网表，就会发现事情没有这么简单。以最通用的 Protel2 为例（节选）：


器件块里全是"编号—网络名"对，网络块里全是"位号—编号"对——整份文件里没有一个引脚名，全是物理编号。各家格式细节略有出入，但气质高度一致：**网表是画完之后从图元里反推出来的导出物，是设计的结果，不是设计的思想。**

问题很直白：

1. **引脚全是物理编号，没有语义。** 这是最大的问题，语言模型天生难处理。
2. **同名引脚全部物理展开。** 设计模型要枚举、要数数——而模型数数是真会数错的。
3. **七种格式七种语法。** 你说用哪一种？
4. **模型没大量学过。** 这种格式的样本量在互联网中太少，没有充分训练，生成错误率自然高。

那怎么办？自己造一个。

## 自己造一个：电路设计 IR 语言

IR 全称 Intermediate Representation，中间表示。你也可以理解为：为大语言模型专门优化的一种极其轻量的网表。

规则一句话：**只写两件事——电路里有哪些器件，哪些引脚电气上连在一起。**

坐标、摆放、封装尺寸、BOM、仿真参数一概不写：要么是绘图 Agent 的活，要么根本不属于"设计意图"这一层。纯 unicode 的 JSON，一个多余字段都不留。

同一个 STM32 最小系统，IR 长这样：

```json
{
  "design": "STM32F405 最小系统",
  "parts": {
    "U1": {"type": "MCU", "part": "STM32F405RGT6", "attrs": {"package": "LQFP64"}},
    "Y1": {"type": "XTAL", "value": "8MHz"},
    "C1": {"type": "CAP", "value": "22pF"},
    "C2": {"type": "CAP", "value": "22pF"},
    "C3": {"type": "CAP", "value": "100nF", "note": "VDD 去耦"},
    "R1": {"type": "RES", "value": "10k", "note": "NRST 上拉"},
    "SW1": {"type": "SWITCH", "value": "tact", "note": "复位按键"},
    "J1": {"type": "CONN", "value": "1x4 2.54mm", "note": "SWD 烧录口"}
  },
  "nets": {
    "OSC_IN":  {"pins": ["U1.PH0", "Y1.1", "C1.1"]},
    "OSC_OUT": {"pins": ["U1.PH1", "Y1.2", "C2.1"]},
    "GND":     {"pins": ["U1.VSS", "Y1.3", "C1.2", "C2.2", "C3.2", "SW1.2", "J1.4"], "kind": "gnd"},
    "3V3":     {"pins": ["U1.VDD", "C3.1", "R1.2", "J1.1"], "kind": "power"},
    "NRST":    {"pins": ["U1.NRST", "R1.1", "SW1.1"]},
    "SWDIO":   {"pins": ["U1.PA13", "J1.2"]},
    "SWCLK":   {"pins": ["U1.PA14", "J1.3"]}
  }
}
```

看见没有：是 JSON，和嘉立创官方的网表是一个族系，并且我在逻辑上进行了重构处理，模型可以复用整个嘉立创的生态。几秒就能读完，一个网络一行，`U1.VDD` 只写一次。

下面几个取舍，每条都是真实争论过的：

- **网络分组，不写边表。** 连接关系写成"这个网络上挂着哪些引脚"，而不是"A 连 B、B 连 C"的边列表。一个五脚网络，边表要写四条边，分组只写一行；边表还容易写出断链和不一致，网络分组天然不会。
- **写引脚名，不写引脚号。** `GPIO0` 是描述思想，物理 pad 号是描述结构，IR 要前者。芯片上大量引脚重名（VDD×3、VSS×3）怎么办？裸名 `U1.VSS` 只写一次，语义是"U1 上所有叫 VSS 的引脚"，由持有器件库的绘图侧展开到每个物理脚——设计模型写一次就够，不用枚举，更不用碰引脚号。极特殊情况（信号地与功率地经磁珠分开）留了 `VSS_1` / `VSS_2` 后缀逃生口，且同一器件上裸名与后缀禁止混用。
- **局部节点用 N1、N2。** 电阻电容之间那种没有功能语义的中间节点，也必须有个名字（JSON 的键就是网络的唯一手柄，格式上不存在匿名网络），规定用 N 加顺序数字：便宜、可读、不编语义名。有功能语义的网络才配语义名。
- **注释分两层。** 严格 JSON 不支持注释，`//` 直接解析失败。对象级注释走 `note` 字段；复杂设计另附一份自然语言姊妹文档 `handover.md`，放设计取舍、敏感区域提示、绘图偏好。铁律是：IR 必须自足，**连接关系永远只存在于 IR 里**，交接文档一个字都不许写连接——否则两份文件必然失同步。
- **大设计允许分块。** 每块都是完整合法的 IR，位号跨块不重叠，同名网络跨块自动合并。长设计不用憋一口气吐完。

## 不指望模型自觉，指望校验器卡门

格式再好，模型也可能会因为错误而不遵守。我的态度是：与其教模型自我审查，不如用定死的脚本让违规输出根本过不去。

| 层 | 谁做 | 查什么 |
|---|---|---|
| 机械规则（设计 Agent） | 校验器（零依赖 Python 单文件） | 结构合法性、引用存在性、一引脚至多一个网络、裸名后缀混用、差分对配对、命名与 kind 匹配、用词一致性 |

实测数据（2026-10-17）：规范内 4 个正例全部零错误过检；8 个构造反例（短路、幻觉器件、裸名后缀混用、地错标电源、差分落单）全部按预期拦成错误，单引脚网络拦成警告；强弱两档模型同题各生成一份 IR，均 0 错误 0 警告。

## 最后

所有的文件都打包在了三个压缩包中（见本仓库 Release）：

- `circuit-ir-design.zip` —— 设计 Agent 的设计技能包
- `circuit-ir-draw.zip` —— 画图 Agent 的绘图技能包
- `easyeda-api-skill-main.zip` —— 立创官方 `easyeda-api-skill` 包（绘图技能包需搭配使用）

其中，画图技能包需要搭配立创官方的包使用。可以让两个 Agent 是平级关系，也可以让绘图 Agent 作为设计 Agent 的子代理。

最重要一点：**本设计没有优化任何 AI 绘制 PCB 相关的内容**，因为我认为那个目前不具备生产可用性。语言模型无法理解复杂的热、电磁、三维空间，这个还得上人。
